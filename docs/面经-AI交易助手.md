# AI Trading Copilot 项目面经

> 事实口径：项目处于 interview project 阶段。以下技术事实来自当前仓库；“主导、独立负责、上线、用户采用”等 Ownership/Result Claim 未经仓库证明，使用前必须按个人真实情况补充。

## 1. 项目简介（简历可用）

AI Trading Copilot 是面向美股与 ETF 的本地交易研究辅助系统，以订阅池限定研究范围，通过结构化多智能体汇聚技术面、新闻情绪与基本面证据，再由确定性风控收紧仓位并生成可解释的组合建议；系统同时提供基本面混合 RAG、版本化交易记忆、Web/CLI 入口、Trace 审计和离线评测。

## 2. 简历 bullet（候选稿）

- **结构化决策编排：** 针对多源分析容易字段漂移、链路难追踪的问题，基于 Pydantic 状态契约和 LangGraph 条件路由组织分析扇出、证据汇聚与顺序决策，并保留缺少编排依赖时的顺序降级，使各 Agent 的输入、输出和失败边界可由代码与测试核验。
- **确定性风险治理：** 针对 LLM 建议不可完全复现的问题，将机会判断、资格检查、单标的仓位上限和组合总敞口约束下沉为代码门禁；风控后的权重才进入组合动作映射，记忆与模型解释均不能扩大限额、反转方向或阻止降低风险的动作。
- **分域检索增强：** 针对基本面资料与交易经验可信度、更新频率和权限不同的问题，拆分基本面 Chroma RAG 与 SQLite 交易记忆：前者采用查询改写、向量/BM25、RRF、重排与父上下文聚合，后者先硬过滤生命周期和范围再排序，降低跨域知识混用风险。
- **受控记忆闭环：** 针对运行后反思可能放大错误经验的问题，设计 Candidate→Shadow→Approved 生命周期、延迟市场结果门禁和追加式版本回滚；Shadow 只记录真实运行命中而不注入 Prompt，只有通过门禁的 Approved 记忆能进入有界检索上下文。
- **可观测运行治理：** 针对多 Agent 故障定位和复盘困难的问题，为节点、工具、LLM、规则命中、耗时与错误建立本地 Trace，并通过 RunTracker 输出状态、阶段报告和审计索引，支持 Web 轮询、取消以及 OTLP/Jaeger 调试。
- **多层质量验证：** 针对功能正确不等于安全与模型质量的问题，建立 pytest 回归、工作流/单 Agent smoke、RAG 检索指标和固定 Memory/Safety/Prompt holdout；当前工作树已验证 229 项测试与 11 项固定门禁全部通过，线上质量、成本和收益指标仍待实测。

## 3. 面试问题（15 个主问题，按频率排序）

### 主题一：项目定位与架构

#### 主问题 1：请用三分钟介绍这个项目。

**第一人称口播版：** 我做这个项目的背景是，主动投资者面对行情、新闻、基本面和组合风险时，信息分散且决策容易受情绪影响；如果直接让大模型给买卖结论，又缺少可复现的安全边界。我的任务是把这个高不确定场景拆成可验证的软件流程。我用订阅池限制研究范围，以结构化 Agent 并行收集证据，Trader 生成计划，确定性 Risk Manager 收紧权重，Portfolio Manager 输出组合动作，并把节点、工具和规则写入报告与 Trace。当前结果是 Web 与 CLI 都能运行，229 项测试和 11 项固定安全门禁通过；但真实用户、线上延迟与收益效果还没有足够证据，需要继续测量。

**追问 1：这个项目和普通“问大模型买什么”有什么差别？**

**第一人称口播版：** 我观察到普通聊天式方案的问题不是不会生成文字，而是输入范围、证据来源、输出结构和风险责任都不清楚。于是我先把机会来源限定为用户订阅池，再让不同分析模块输出 Pydantic 结构，最终建议必须经过代码级资格和仓位门禁。这样模型仍负责综合与解释，但不能凭一段自然语言绕过风险限制。结果上，我能用节点覆盖、结构化输出和安全比较做离线验证，也能从 Trace 追到某个建议用了什么数据；尚缺的是与真实用户决策耗时和误推荐率的对照实验。

**追问 2：你认为这个项目最有价值的部分是什么？**

**第一人称口播版：** 我认为最大价值不是 Agent 数量，而是把概率推理关进确定性边界。场景中真正危险的是模型可能自信地给出超仓、追高或引用未经验证经验的建议，所以我把最终权重计算、禁用品种、总敞口和确认要求放在程序规则里，同时让错误和数据缺失显式进入状态。当前 11 项固定 Harness 能证明记忆隔离、风险不能被放大、版本回滚和 Prompt 合约没有回归；但它不能证明策略能赚钱，这个边界我会主动向面试官说明。

#### 主问题 2：为什么采用订阅池驱动，而不是全市场扫描？

**第一人称口播版：** 我把订阅池当成产品边界和安全边界，而不仅是一个列表功能。用户本来就会长期维护少量有研究基础的标的，全市场自由推荐会放大数据成本、幻觉风险和注意力噪声，也难以解释为什么某只股票突然进入结果。我的做法是让订阅记录同时携带市场类型、状态、关注理由和目标动作，风控再校验计划是否来自允许范围。结果是机会资格可以被程序化测试，越界请求会保持当前仓位不动。代价是可能漏掉池外机会，后续可把市场雷达作为独立、只生成候选而不直接交易的扩展层。

**追问 1：订阅池会不会严重限制发现能力？**

**第一人称口播版：** 会，所以我把它视为有意识的取舍，不把它包装成万能方案。第一阶段目标是帮助已有研究框架的用户提高决策纪律，而不是替代选股研究；在这个目标下，限制范围能显著提升可解释性和数据预算可控性。如果未来需要扩展发现能力，我会增加一个独立的机会雷达，让它只把候选送入人工审核或订阅池，不能直接进入交易计划。验证时会比较池内任务完成率、池外候选采纳率和误推荐率，而当前这些真实用户数据仍待补充。

**追问 2：订阅状态如何流转？**

**第一人称口播版：** 我把状态设计为 observing、near_opportunity、actionable、risk_elevated 和 not_compatible，用来表达从持续观察到可行动以及风险升高的不同阶段。技术、新闻和基本面证据会影响状态，但状态不是最终订单；Trader 还要生成包含止损和失效条件的计划，Risk Manager 再校验资格与权重。这样的分层避免一个情绪分数直接触发交易，也让 UI 能解释“为什么等待”。当前状态迁移和边界有单测覆盖；真实状态与后续走势的一致性还需要历史回放验证。

#### 主问题 3：为什么使用多智能体和 LangGraph？

**第一人称口播版：** 我的出发点不是为了堆 Agent，而是因为技术面、新闻和基本面的输入源、失败方式、输出字段不同，适合并行隔离；Trader、风控和组合决策又存在严格依赖，必须顺序执行。我用 LangGraph 表达条件扇出与汇聚，用共享状态而非自由对话传递结构化证据，并实现同一节点顺序的 sequential fallback。这样用户可以按需选择分析模块，单个分析源失败也能被单独记录。当前工作流 smoke 验证了 10 个必需节点和 8 类报告覆盖；并行对真实外部调用的加速比例还没有基准数据。

**追问 1：不用 LangGraph、只写普通函数不行吗？**

**第一人称口播版：** 在 MVP 很小时普通函数完全可行，所以我保留了顺序执行路径。选择状态图的原因是分析节点存在条件选择和天然扇出，运行还需要逐节点进度、取消、报告索引和 Trace；显式图结构能让路由和依赖更容易测试。代价是状态合并、并发写入和调试复杂度上升，因此我没有把运行后记忆学习也塞进主图，而是作为主流程完成后的服务。若项目规模不再增长，我不会继续抽象新的编排层；是否值得要由节点数量、变更频率和并行收益决定。

**追问 2：并行节点怎样避免状态覆盖？**

**第一人称口播版：** 我把并行结果按字段职责拆分，例如技术上下文、新闻报告、基本面报告和各自的报告路径分别存储；需要累加的 TraceEvent 使用追加语义，需要合并的报告字典使用字典合并，其他字段则由拥有者节点写入。这样每个节点的写集合相对明确，Trader 只在汇聚点读取完整证据。当前测试覆盖了 LangGraph 路由和状态汇聚，但对于真实高并发、节点重复执行和持久化竞争，还缺少压力测试和故障注入结果，这部分会列为待补充。

### 主题二：决策与安全边界

#### 主问题 4：如何约束 LLM 生成的交易计划？

**第一人称口播版：** 我把约束分成结构、语义和组合风险三层。结构层用 `TradePlan` 模型要求方向、入场逻辑、止损、目标、权重、持有期和失效条件；语义层在 Trader 输出后执行确定性买入门禁，例如机会必须 actionable、收益风险比至少 2、距支撑不超过 3%、没有重大新闻或基本面风险，也不能追高；组合层再由 Risk Manager 做资格和权重 clamp。结果是模型输出即使格式正确，也不能自动获得执行资格。当前安全路径有单测和 Harness，阈值在不同市场状态下的有效性仍待历史验证。

**追问 1：为什么收益风险比阈值设为 2？**

**第一人称口播版：** 这个值在当前实现里是明确的工程默认值，用于让买入门禁可复现，而不是来自已经证明最优的统计结论。我会向面试官区分“产品规则”和“策略研究结果”：规则的好处是容易测试和解释，风险是固定阈值可能在波动率、行业或市场状态变化时失效。下一步应该在冻结数据集上按市场状态分层回放，比较不同阈值下的触发率、后续收益、最大回撤和样本量，再决定是否做配置化或动态化；当前不能宣称 2 是最佳值。

**追问 2：如果 LLM 返回非法 JSON 或缺字段怎么办？**

**第一人称口播版：** 我为关键 Agent 都保留了确定性 fallback。系统先基于现有结构化证据生成保守计划，再尝试解析模型 JSON；解析失败、调用异常或工具不可用时回到 fallback，并把异常写入状态与 Trace，而不是伪装成正常的智能分析。即使模型返回可解析字段，最终仍会重新构造 Pydantic 模型并执行安全门禁。这样做牺牲了一部分生成灵活性，但保证失败模式可预测。当前离线 smoke 能覆盖回退结构，真实供应商超时、限流和半响应场景还需要系统化故障注入。

#### 主问题 5：Risk Manager 具体怎么做仓位限制？

**第一人称口播版：** Risk Manager 接收 Persona、订阅池、当前组合、交易计划和目标权重。它先做资格检查，发现池外标的、市场不允许、杠杆或期权等情况时，把目标权重保持在当前值；对合格标的先按正负方向限制到单标的绝对权重上限，再计算全组合 gross exposure，若超限则按同一比例缩放所有最终权重。每次缩放会留下 before、after、reason 和 limit。结果权重再交给 Portfolio Manager 转成 buy、sell、reduce、short、cover 或 hold。当前边界有测试保护，真实组合回放和极端行情测试待补充。

**追问 1：为什么总敞口超限时按比例缩放？**

**第一人称口播版：** 比例缩放的优势是确定、简单，并能保持各目标仓位的相对结构，不需要让模型在风险阶段重新排序或临时分配资金。它也符合“风控只削减风险、不创造新交易意图”的职责边界，削减出来的敞口直接保留为现金。缺点是没有考虑不同标的流动性、相关性和信号置信度，可能把高质量与低质量机会同幅削减。下一步可以在不破坏硬上限的前提下增加可解释的优先级优化，但必须用历史组合和压力场景验证，而不是让 LLM 自由重分配。

**追问 2：记忆能影响最终权重吗？**

**第一人称口播版：** 可以影响，但只能向更保守方向影响。Portfolio Manager 只有在风控结果会增加绝对敞口时才检索 Approved Memory，模型只能选择 proceed、scale 或 hold，缩放系数被程序限制在 0 到 1；没有真实引用时不能缩小，且记忆不能扩大仓位、反转方向，也不能阻止减仓或平仓。这样历史经验是风险侧上下文，而不是新的交易指令。Harness 已验证不能放大风险上限和不能阻止风险降低，记忆长期有效性仍需依赖 Shadow 延迟结果。

#### 主问题 6：系统是否会真实下单？如何防止误操作？

**第一人称口播版：** 项目定位是研究辅助，不支持 Live 真实券商订单。主工作流只生成组合决策，不直接提交订单；当使用 Futu `SIMULATE` 时，结果页会显示候选动作，用户必须再次明确确认，后端还会校验 run、symbol、风险批准、数量和幂等键后才调用模拟适配器。Live portfolio 只能作为只读上下文，代码不调用解锁真实交易。这样把“生成建议”和“提交模拟单”拆成两个用户动作。当前相关 API 和测试已覆盖，真实账户安全审计、权限模型和合规评审仍待补充。

**追问 1：为什么 simulation 也要二次确认？**

**第一人称口播版：** 我希望用户在产品心智上始终区分分析结论与执行动作。即使是模拟单，如果系统自动提交，用户也可能误以为相同链路能安全迁移到真实交易，而且难以观察最终数量、方向和风险调整。因此运行只产出 pending candidate，用户在结果页复核后再确认，后端使用幂等键避免重复提交。这个设计增加了一步操作，却换来更清晰的责任边界和可审计性。后续应补充重复点击、网络重试和适配器异常的故障演练结果。

**追问 2：未来支持 Live 交易要补什么？**

**第一人称口播版：** 我不会把现有模拟确认按钮简单改成 Live。需要新增强认证与交易解锁、权限和额度模型、订单预览、价格偏离与时效校验、幂等和状态对账、撤改单、交易时段与合规限制、审计留存以及紧急停机机制，还要把风险规则做独立安全评审。最重要的是明确人机责任和失败恢复，而不是只接一个 broker API。当前仓库明确不支持 Live order，所以面试中我会把这些作为未来设计，不会声称已经实现或验证。

### 主题三：RAG 与记忆

#### 主问题 7：为什么把基本面 RAG 和交易记忆拆开？

**第一人称口播版：** 两类知识的语义和可信度不同。基本面 RAG 存年报、季报、指引和研究笔记，目标是帮助 Fundamental Analyst 找到公司证据，最新工具数据仍优先；交易记忆来自历史运行反思，可能包含错误归因，所以需要版本、状态、有效期和审批。我的做法是 Chroma 只承载基本面材料，SQLite 作为交易记忆唯一事实源，另有可重建本地向量侧索引。结果是使用者和安全策略都清楚，分析师不会被历史交易经验污染；代价是两套存储与检索要分别维护。

**追问 1：为什么 SQLite 是事实源，向量索引只是 sidecar？**

**第一人称口播版：** 记忆需要事务化记录当前版本、历史版本、状态迁移、运行命中、延迟结果和评测，而向量库更适合相似度召回，不适合承担全部审计语义。因此我让 SQLite 保存规范化记录和生命周期，向量 sidecar 只保存可重建表示；若索引丢失，可以从事实源重建，不影响审批历史。这个选择适合本地单用户 MVP，也便于测试回滚。它的限制是横向扩展和多实例并发能力有限，未来若迁移托管存储，仍应保持“事实与索引分离”的契约。

**追问 2：如何避免两套知识互相矛盾？**

**第一人称口播版：** 我先通过调用权限减少冲突：基本面 Agent 只读取公司材料，Trader 和受限 Portfolio Advisor 才读取 Approved 交易记忆；然后在 Prompt 与代码中明确实时行情、最新工具数据和确定性风控优先，记忆只能作为历史参考。每次采用的记忆必须引用 `memory_id@version`，伪造引用会被过滤，并在运行末生成检索审计。仍可能出现内容层矛盾，所以后续要增加证据时间、来源质量和冲突检测指标；当前还没有完整的冲突评测集。

#### 主问题 8：基本面 RAG 为什么采用混合检索？

**第一人称口播版：** 财务材料既有语义表达，也有代码、指标和专有名词。纯向量可能漏掉精确词，纯关键词又难处理改写和同义问题，所以我把请求扩展成基础、风险、技术和基本面查询，分别走向量与 BM25 召回，用 Reciprocal Rank Fusion 合并排序，再做本地特征重排，最后把子块聚合回父上下文。这样提示词不会塞入整份报告，同时保留段落上下文。代码已实现检索链和评测指标，但当前没有可靠的真实 RAGAS 跑分，不能声称质量提升百分比。

**追问 1：为什么使用父子分块？**

**第一人称口播版：** 小块更利于精确召回，但直接把小块交给模型可能缺少标题、财期和上下文；大块上下文完整，却会降低召回粒度并增加 token。父子分块让检索在 child 上发生，再按 parent 聚合并把较完整语义交给 Fundamental Analyst，同时用 metadata 保留 section、source、symbol 和 fiscal 信息。它的风险是父块过大或多个 child 指向重复上下文，导致冗余。需要用 context precision、token 成本和答案忠实度一起调参，当前这些真实结果仍待补充。

**追问 2：RRF 相比直接合并分数有什么好处？**

**第一人称口播版：** 向量相似度和 BM25 分数不在同一尺度，直接加权需要做稳定的归一化，而且不同数据集上权重敏感。RRF 只依赖各通道排名，用倒数排名累加，因此实现简单、对分数尺度更稳健，适合作为本地混合检索的基线。它也有局限：忽略原始置信度，参数和候选深度仍会影响结果，所以我后面加了本地重排和 metadata boost。是否优于关键词基线必须通过 hit@k、MRR、NDCG 和上下文精确率实测，当前文档只给出门槛，没有完成线上评测。

#### 主问题 9：交易记忆生命周期是怎么设计的？

**第一人称口播版：** 一次运行结束后，LangMem Reflector 只从结构化证据提炼 insert/update 提案，Skill Manager 做去重或候选合并，初始状态是 Candidate。人工确认后可进入 Shadow，运行时用相同查询记录命中但不注入 Prompt；积累至少 3 个不同运行命中和 3 份延迟结果，并通过置信度、相对基准收益、回撤和安全语义门禁后，才允许成为 Approved。Rejected 和 Deprecated 保留审计。任何更新与回滚都创建新版本，这样我能追溯当时实际使用的是哪一版记忆。

**追问 1：为什么 Shadow 不直接给模型看？**

**第一人称口播版：** Shadow 的任务是收集“如果这条记忆在当时相关，之后结果如何”的证据，而不是参与生产决策。如果它进入 Prompt，就会改变交易计划，随后无法区分结果来自原流程还是来自候选记忆，同时错误经验也可能提前影响用户。于是我让 Shadow 走同样的硬过滤和相关性查询，只登记命中，不返回给 Agent。代价是评测周期更长，但能获得更干净的反事实近似。当前 Harness 验证 Shadow 不注入，真正的市场因果评估仍需要更大样本和更严格实验。

**追问 2：如何防止 LLM 伪造记忆引用？**

**第一人称口播版：** 检索会话保存本次实际返回的 Approved 记忆集合，模型输出 `memory_citations` 后，程序只接受集合中真实存在的 `memory_id@version`；不在会话结果中的引用会被删除。如果 Portfolio Advisor 想缩小风险，却没有有效引用，缩放会恢复为 1，避免模型用虚假“历史经验”改变权重。采用记录还会区分 trader、trader_applied、portfolio_manager、portfolio_applied 和 shadow。当前有测试和固定门禁保护，仍需补充对恶意 Prompt 注入和脏历史数据的专项评测。

### 主题四：可观测性、评测与工程化

#### 主问题 10：你如何做可观测性？

**第一人称口播版：** 我把每次运行视为一个可审计事务，用 run_id 隔离报告目录和状态。节点开始、成功、失败，工具调用、LLM 请求摘要、规则命中、耗时和错误都会进入本地 Trace，并生成 JSON 与 Markdown；Web 端轮询 RunTracker 展示节点进度和报告索引。需要跨进程查看时，可以把精简且脱敏的属性通过 OTLP 发到 Jaeger，完整内容仍保留本地。这样既能定位问题，也降低敏感文本外发。当前 Trace 有测试和 smoke 证据，真实长时间运行的采样、存储容量和告警策略待补充。

**追问 1：如何处理敏感信息？**

**第一人称口播版：** 我不把完整本地 Trace 原样发送到可观测平台，而是对常见敏感键做识别和脱敏，对大段文本记录摘要、长度或哈希，并限制单个属性大小；详细的请求响应只保存在本地运行目录。这样调试平台可以看到节点瀑布、模型名、耗时和错误类型，但不必接收所有业务内容。风险是敏感识别规则可能漏项，本地报告也需要访问控制和保留策略。当前实现验证了字段处理逻辑，尚缺正式数据分类、威胁建模和安全审计报告。

**追问 2：为什么报告和 Trace 都要保留？**

**第一人称口播版：** 两者面向不同读者。报告把结构化状态转成人能读懂的阶段结论，适合用户复盘；Trace 保留节点、工具、LLM 和规则层的技术证据，适合定位故障。若只保留报告，可能知道“建议保持”却不知道是数据缺失、模型回退还是风险门禁导致；若只保留 Trace，用户又难以快速理解结论。我让 RunTracker 建立报告索引，并确保解释来自同一份状态，减少结论与执行数据不一致。真实用户是否觉得报告好懂仍待可用性测试。

#### 主问题 11：你如何评测这个系统？

**第一人称口播版：** 我把评测分成四层。第一层是 229 项 pytest，验证模型、路由、API、RAG、记忆、风控、模拟执行和 Trace 的功能回归；第二层是工作流与单 Agent smoke，检查节点、报告、字段、决策和安全期望；第三层是 RAG 的 hit@k、recall、precision、MRR、NDCG、延迟和可选 RAGAS 答案质量；第四层是固定 11 项 Memory/Safety/Prompt holdout，防止优化 Prompt 时破坏隔离和硬边界。当前前三类中的离线 smoke 与测试已通过，真实 RAG、线上质量和收益评测仍未完成。

**追问 1：229 个测试通过能证明策略有效吗？**

**第一人称口播版：** 不能。它只能证明当前测试描述的工程行为没有回归，例如超仓会被 clamp、Shadow 不进入 Prompt、API 返回符合预期。策略有效需要独立的数据集、时间切分、交易成本、基准、样本量以及避免未来函数的回测，还要观察最大回撤和不同市场状态。即使离线回测表现好，也不代表未来收益。我会把工程正确性、安全性、检索质量和业务/投资效果分开报告，避免用测试数量替代真实价值。当前项目最大的证据缺口正是历史回放与真实用户评估。

**追问 2：如何避免 Prompt 优化过拟合？**

**第一人称口播版：** 我把 Autoharness 的可编辑面限制在 `config/prompts`，把风险代码、组合管理、评测实现、固定 holdout 和 tests 都列为 protected surfaces；候选 Prompt 必须通过相同 11 项门禁，晋升只提交 Prompt 路径，回滚后也要重跑门禁。这样至少阻止生成器为了得分修改答案或安全规则。仍然可能对固定 Prompt 合约过拟合，所以需要独立隐藏集、真实失败样本和定期扩充评测维度；当前 holdout 更偏安全与隔离，不足以代表决策质量。

#### 主问题 12：系统如何处理外部数据或 LLM 不可用？

**第一人称口播版：** 我把“缺数据”当成一等状态。技术分析数据不足时输出 unknown 或观察结论，新闻和基本面报告带 data availability、uncertainties 与风险字段；Agent 解析或调用失败时回到保守的确定性结果，并把错误写入 Trace。缺少默认 LLM 时主图可以 fail closed，避免把不完整运行包装成智能结论；LangGraph 不可用则走顺序降级。这样系统更可解释，但降级质量并不等于完整分析质量。当前测试覆盖主要失败路径，真实限流、超时、断网、脏数据和跨源冲突的故障矩阵仍待补充。

**追问 1：为什么有时 fail closed，有时继续降级？**

**第一人称口播版：** 取决于能力是否有可信的确定性替代。编排库不可用时，同一批节点仍可按顺序执行，所以可以降级；某个分析源缺数据时，可以明确输出未知并让后续保持观察。但完整多智能体运行如果明确要求 LLM 决策而默认模型完全不可用，继续伪造一份“AI 分析”会误导用户，因此应该 fail closed。核心原则是降级后的语义必须诚实、可解释且不扩大风险。后续要把每类依赖的降级等级、SLO 和用户提示做成明确矩阵，目前尚未形成完整运维规范。

**追问 2：如何避免旧数据误导决策？**

**第一人称口播版：** 当前做法包括在基本面文档 metadata 中保留来源、创建时间、财期和类型，在线工具数据优先于 RAG 背景；交易记忆支持 valid_from、valid_until、状态和范围硬过滤，过期记忆不会进入 Approved 检索。技术和新闻结果也会暴露数据可用性。但时间一致性仍是高风险点，例如财报发布日期、交易日截面和回测未来函数需要更严格的数据契约。当前没有完整的数据新鲜度 SLO 和时间穿越审计，因此我会把它列为上线前必须补齐的内容。

### 主题五：个人贡献、取舍与迭代

#### 主问题 13：你个人负责了什么？

**第一人称口播版：** 【待补充：请按真实情况替换】我在项目中的角色是【个人/团队角色】，负责范围包括【需求分析、架构、某些 Agent、RAG、记忆、UI、测试中的真实部分】；我与【团队人数及协作角色】协作，边界是【哪些模块由他人完成或参考外部项目】。我重点解决的难题是【一个可展开的技术或产品难题】，通过【具体动作和代码/设计证据】完成，并用【测试、演示、指标或用户反馈】验证。仓库能证明系统存在这些能力，但不能自动证明全部由我个人主导，所以面试前必须把提交记录、时间线和职责口径对齐。

**追问 1：哪一部分最能体现你的技术深度？**

**第一人称口播版：** 【待补充：选择本人真正做深的一项】如果选择确定性风控，我会从为什么不能让 LLM 决定最终仓位讲起，展示资格门禁、单标的 clamp、总敞口比例缩放和记忆只能降风险的代码与测试；如果选择记忆系统，我会讲 SQLite 事实源、版本追加、Shadow 不注入和延迟结果门禁。我的回答必须落到我亲自做过的设计、调试和验证，而不是复述 README。结果证据优先使用具体测试、Trace、提交或演示，尚未测的指标明确说明待补。

**追问 2：遇到的最大失败或返工是什么？**

**第一人称口播版：** 【待补充：真实失败案例】建议按 STAR 组织：当时出现【具体现象，例如状态漂移、检索噪声、UI 与后端结论不一致】；我的任务是【约束和目标】；我先用【日志、最小复现、测试或数据对比】定位到【根因】，随后做了【修改】并增加【回归门禁】；最终【可验证结果】。重点不是把故事说成一次成功，而是说明为什么原判断不够、如何缩小问题、怎样防止复发，以及还有什么遗留风险。

#### 主问题 14：项目中最关键的技术取舍是什么？

**第一人称口播版：** 我认为最关键的取舍是可控性优先于自动化程度。项目没有追求全市场自动选股和自动下单，而是使用订阅池、结构化计划、代码级风险规则和二次确认；记忆也不是生成后立即生效，而是经过 Shadow 与审批。这样牺牲了一部分“看起来很智能”的体验和迭代速度，却让每个建议有可解释输入、硬边界和审计证据。当前测试与 Harness 支持这个取舍，但是否显著提升用户信任，需要报告可用性、确认行为和访谈数据；这些产品指标目前仍待补充。

**追问 1：项目有没有过度设计？**

**第一人称口播版：** 有这个风险，尤其是多 Agent、两套知识域、版本化记忆和完整 Trace 同时出现时。我的判断标准是每个机制是否对应明确失败模式：LangGraph 对应条件扇出和进度，双存储对应不同知识生命周期，Shadow 对应错误经验污染，Trace 对应多节点定位。如果某机制没有真实使用或验证，我会把它降级为实验能力而非核心成果。当前本地单用户场景下，托管数据库、微服务和复杂权限都没有引入；下一步也应先补真实评测，而不是继续增加框架。

**追问 2：如果只给两周做 MVP，你会删什么？**

**第一人称口播版：** 我会保留 Persona、订阅池、一个技术分析模块、结构化 TradePlan、确定性 Risk Manager、简单报告和纯模拟建议，因为它们构成最小价值与安全闭环。新闻、基本面 RAG、长期记忆、Jaeger 和复杂 UI 可以分阶段加入；先用固定数据和 CLI 验证端到端，再加 Web。这样能更快回答用户是否需要“纪律化自选池分析”。当前仓库能力较完整，但面试时我会强调演进顺序和为什么增加某模块，而不是把所有依赖描述成第一天就需要。

#### 主问题 15：下一步最优先补什么？

**第一人称口播版：** 我会优先补证据，不先堆功能。第一是建立无未来函数的历史回放，明确样本区间、交易成本、基准、机会触发率、收益和最大回撤；第二是在真实 LLM 与数据源下测端到端 P50/P95、失败率、降级率和成本；第三是跑完整 RAG 评测并补时间一致性与冲突样本；第四是加 CI、覆盖率、静态检查和并发故障注入。产品侧再做 5 到 10 名目标用户可用性测试，观察报告理解和决策耗时。只有这些完成后，才能判断哪些 Agent 或记忆机制真的产生价值。

**追问 1：如果只能选一个指标，你选什么？**

**第一人称口播版：** 如果处于当前 interview/MVP 阶段，我会选“可复现的安全合格运行率”，定义为在固定输入和依赖条件下，任务无错误完成、结构化输出齐全、风险门禁正确、报告可追溯的比例。它比单纯延迟或收益更符合当前成熟度，也能阻止为了展示效果牺牲安全。进入真实用户阶段后，我会把北极星指标调整为“用户完成一次可解释决策所需时间”并搭配误推荐和风险违规护栏。当前仓库已有组成指标，但尚未建立持续看板和真实基线。

**追问 2：怎样证明多 Agent 比单 Agent 更好？**

**第一人称口播版：** 不能用架构复杂度证明。我会设计同一历史截面、相同数据预算和相同最终风控下的 A/B：单 Agent 直接生成计划，对比多模块证据汇聚方案，测结构完整率、关键风险召回、建议一致性、错误率、延迟、token 成本和人工评分，并按市场状态分层。风控必须保持一致，避免把安全差异误归因于推理能力。若多 Agent 只增加成本而质量没有显著提升，就应合并模块。当前项目只有组件级和工作流 smoke，没有完成这类消融实验，所以这是高优先级待补项。
